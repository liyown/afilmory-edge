# Architecture

Afilmory runs as one Cloudflare Worker. The same deployment serves the gallery SPA at `/`, the admin dashboard at `/platform/`, and the API under `/api`.

## Components

### Worker (`apps/edge`)

The Worker owns:

- static assets for the gallery and dashboard
- the API graph from `be/apps/core` (`@tsuki-hono` modules, controllers, and DI)
- per-request manifest injection into `index.html`
- dynamic OG images, SEO metadata, sitemap, feed, and well-known routes
- scheduled backup and cleanup jobs

`apps/edge/cloudflare.config.ts` declares the bindings: `DB` (D1), `PHOTOS` (R2), `CACHE` (KV), and `ASSETS`.

### D1

D1 stores users, sessions, photos, manifests, comments, settings, and manifest-sync revisions. The schema lives in `be/packages/db/src/schema.ts`; migrations are generated into `be/packages/db/migrations`.

There is a single baseline migration. The project targets a fresh database and does not carry historical migration chains.

### R2

R2 stores uploaded photos, video companions for Live Photos, generated manifests, cached OG images, and D1 backups. Uploads can use presigned URLs when R2 S3 credentials are configured; otherwise the Worker proxies the bytes.

### KV

KV caches the serialized manifest and revision metadata so reads avoid rebuilding the manifest on every request. It is an accelerator, not the source of truth.

### Builder (`packages/builder`)

The builder is a Node CLI for bulk photo processing: it syncs from storage providers, normalizes formats, extracts EXIF, generates thumbnails and ThumbHash placeholders, and writes `photos-manifest.json` for standalone builds and demo data.

The Worker does not run the builder. Runtime uploads are handled by the Worker upload path, which stores objects in R2 and extracts metadata from range reads.

## Request Flow

```
Browser
     │
     ▼
Cloudflare Worker (apps/edge)
     ├── ASSETS      → gallery SPA, dashboard SPA
     ├── core API    → auth, photos, comments, settings, feed
     ├── D1          → relational state
     ├── R2          → photo objects, backups, OG cache
     └── KV          → manifest cache
```

The Worker reads published photo records from D1, builds the manifest on demand, and injects it into the SPA shell as `window.__MANIFEST__`. Manifest revisions let clients and caches invalidate deterministically after an upload or edit.

## Upload Flow

1. The dashboard requests an upload intent from the Worker.
2. The Worker returns a presigned R2 URL (or accepts a proxied upload).
3. On completion, the Worker verifies the object, extracts metadata, and writes the photo asset to D1.
4. A manifest revision is allocated and the manifest cache is invalidated.
5. The gallery picks up the change on the next manifest fetch.

## Authentication

Better Auth runs inside the Worker with the Drizzle D1 adapter. Registration is disabled; the owner account is created by `pnpm bootstrap:admin`. OAuth callbacks can be brokered by `be/apps/oauth-gateway`, an optional standalone service.

## What Is Not Here

There is no tenant resolution, subdomain routing, billing, per-user storage configuration, Redis, or task queue. The deployment is intentionally single-owner.
