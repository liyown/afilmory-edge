# Architecture

Afilmory runs as one Cloudflare Worker. The same deployment serves the gallery SPA at `/`, the admin dashboard at `/platform/`, and the API under `/api`.

## Components

### Worker (`apps/edge`)

The Worker owns:

- static assets for the gallery and dashboard
- the API graph from `be/apps/core` (`@tsuki-hono` modules, controllers, and DI)
- the photo upload pipeline: upload intents, OSS writes, EXIF/XMP extraction, Live/Motion Photo detection
- per-request manifest and site-config injection into `index.html`
- dynamic OG images, SEO metadata, sitemap, feed, and well-known routes
- scheduled backup and cleanup jobs

`apps/edge/cloudflare.config.ts` declares the bindings: `DB` (D1), `CACHE` (KV), and `ASSETS`. Object storage is configured through the `S3_*` Worker secrets.

### D1

D1 stores users, sessions, photos, manifests, comments, settings, and manifest-sync revisions. The schema lives in `be/packages/db/src/schema.ts`; migrations are generated into `be/packages/db/migrations`.

There is a single baseline migration. The project targets a fresh database and does not carry historical migration chains.

### OSS

Aliyun OSS stores uploaded photos, generated 600px thumbnails (`<key>-thumb.jpg`), video companions for Live Photos, `manifest.json`, cached OG images, and D1 backups. The bucket is private: uploads use presigned S3 URLs, and visitors read media through the Worker's `/media/*` proxy.

### KV

KV caches the serialized manifest so shell requests avoid reading OSS on every page view. It is an accelerator, not the source of truth.

## Request Flow

```
Browser
     │
     ▼
Cloudflare Worker (apps/edge)
     ├── ASSETS      → gallery SPA, dashboard SPA
     ├── core API    → auth, photos, comments, settings, feed
     ├── D1          → relational state
     ├── OSS         → photo objects, manifest, backups, OG cache
     └── KV          → manifest cache
```

The Worker reads published photo records from D1, builds the manifest, and injects it into the SPA shell as `window.__MANIFEST__`. Uploads and edits clear the KV cache immediately.

## Upload Flow

1. The dashboard requests an upload intent from the Worker.
2. The Worker returns a presigned OSS URL.
3. The dashboard renders a thumbnail, ThumbHash, and tone analysis in the browser.
4. On completion, the Worker verifies the object, extracts EXIF/XMP with range reads, detects Live/Motion Photos, and writes the photo asset to D1.
5. `ManifestPublisher` rebuilds `manifest.json` in OSS and clears the KV cache.
6. The gallery picks up the change on the next shell request.

## Authentication

Better Auth runs inside the Worker with the Drizzle D1 adapter. Registration is disabled; the owner account is created by `pnpm bootstrap:admin`. OAuth callbacks can be brokered by `be/apps/oauth-gateway`, an optional standalone service.

## What Is Not Here

There is no tenant resolution, subdomain routing, billing, per-user storage configuration, Redis, or task queue. There is also no separate build-time photo pipeline: every upload goes through the Worker.
